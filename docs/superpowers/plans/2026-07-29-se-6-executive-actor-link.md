# SE-6 임원 ↔ 행위자 연결 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 임원 이름이 화면에 글자로만 놓여 있는 상태를 없앤다. 그 이름이 레지스트리에 있으면 **그 사실을 화면이 먼저 말하고**, 눌러서 근거를 볼 수 있게 한다.

**Architecture:** 서버에 이름 단위 조회를 더한다(지금은 회사 단위뿐). 클라이언트는 임원 명단 전체를 한 번에 대조해 표에 표시를 달고, 이름 클릭 시 기존 우측 패널을 연다. 대조 판정은 `app.js`의 순수 함수, 조회는 `se_server`.

**Tech Stack:** Python(se_server), 순수 ES5 스타일 JS, pytest + node 서브프로세스.

## Global Constraints

- **⚠️ 이 계획은 실명을 다루고, 잘못하면 무고한 사람을 지목한다.** 아래 "말할 수 있는 것과 없는 것"을 어기는 문구가 하나라도 화면에 나가면 안 된다. 이 제약이 다른 모든 것보다 우선한다.
- **판정 금지 (v0.8.5).** 점수·등급·순위 없음. 레지스트리는 사실 표기다.
- **`dart_risk_mcp/`는 손대지 않는다.** 조회 함수(`lookup_actor`·`actor_status`)는 이미 있다. MCP 도구 26개 무영향.
- **외부 의존성 추가 금지.**
- **DOM 주입 금지.** 데이터는 `textContent`로만.
- **다크·라이트 양쪽 정의.** 새 CSS 변수는 `:root`와 `:root[data-theme="light"]` 양쪽에.
- **로그아웃 잔류 금지.** 실명이 화면에 남으면 안 된다 — 이 저장소는 이미 두 번 겪었다.

## 말할 수 있는 것과 없는 것

**이것이 이 계획의 핵심이다. 나머지는 배선이다.**

| ✅ 말할 수 있다 | ❌ 말하면 안 된다 |
|---|---|
| `같은 이름 표기가 레지스트리에 있습니다` | `이 임원이 다른 회사에도 등장합니다` |
| `레지스트리 등재: FSN · 위노바` | `이 사람은 FSN·위노바에도 관여했습니다` |
| `동명이인일 수 있습니다 — 확인은 이용자 몫입니다` | (경고를 생략하거나 접어두는 것) |
| `status: auto_matched (기계 매칭)` | `검증됨`으로 읽히는 표기 |

**근거(실측):** 레지스트리 개인 545명 중 **522명이 한글 2~4자 순수 인명**이고, 그중 **99.5%가 `auto_matched`** — 기계가 이름만 보고 맞춘 것이며 동일인 검증이 없다. 임원 응답에는 `birth_ym`(생년월)이 있지만 **레지스트리에는 없다**(인수자 명단에서 온 데이터라 생년이 없다). 즉 **자동으로 동일인을 가릴 방법이 없다.**

### ⚠️ 동명이인 판별을 **시도하지 않는다** (2026-07-29 결정)

수십~수백 명의 동명이인을 우리가 가려 주는 것은 이 도구가 질 수 있는 부담이 아니다. 생년월도 없고, 틀리면 무고한 사람을 지목한다.

**대신 경고를 실행 가능하게 만든다.** "확인되지 않았습니다"로 끝내면 이용자가 무엇을 해야 할지 모른다. **어떻게 확인하는지까지 화면이 말한다:**

1. **근거 공시 원문** — 레지스트리 기록의 DART 링크
2. **법인 등기 기록**
3. **회사·본인에게 직접 문의**

그래서 화면이 하는 일은 **"이름이 같다"는 사실 전달 + 확인 방법 안내**까지다. 동일인 판단은 이용자가 한다.

**동명이인 경고는 접거나 툴팁에 숨기지 않는다.** 표시와 같은 자리에 항상 보여야 한다.

### 근거 공시는 DART 링크로 연다 (실측)

레지스트리 기록 1,342건 중:

| 필드 | 보유 | 쓸모 |
|---|---:|---|
| `url` | **1,337건 (100%)** | DART 원문 직접 링크 — **이걸 쓴다** |
| `evidence` | 1,342건 (100%) | 근거 문장 |
| `rcept_no` | **45건 (3%)** | 내부 원문 패널용 — **비율이 낮아 의존하면 안 된다** |

**`openDocPanel(rcept_no)`에 기대지 마라.** 97%가 `rcept_no`가 없다. `url`을 외부 링크로 연다.

**⚠️ `url`을 그대로 앵커에 넣지 마라.** 레지스트리는 Notion에서 오는 외부 데이터다. **호스트가 `dart.fss.or.kr`인 것만** 링크로 만들고, 아니면 링크 없이 텍스트로만 둔다. `add_registry_record`가 `disclosure_url()`로 구성해 넣지만, 저장소를 신뢰해 렌더 규칙을 느슨하게 할 이유가 없다.

**응답 형태 — `?company=`와 같은 껍데기를 쓴다:**

```json
{
  "name": "이승호",
  "actors": [
    {"name": "이승호", "status": "auto_matched",
     "companies": ["FSN", "위노바"], "evidence": "..."}
  ],
  "disclaimer": "..."
}
```

**요구사항:**

- `?name=`과 `?company=`가 **동시에** 오면 400. 둘 다 없어도 400. 어느 쪽인지 모호한 요청에 답하지 않는다.
- **레지스트리를 못 가져온 것과 이름이 없는 것을 구분한다.** SE-5c가 `load_known_actors_with_source()`로 그 구분을 만들었다 — `bundled` + opt-in이면 502, 그 외 미발견은 `200 + 빈 목록`. `?company=` 분기가 이미 그렇게 하고 있으니 **같은 방식을 쓴다.**
- 인증 가드는 기존과 동일(변경 없음).
- 응답에 **면책 문구를 반드시 싣는다**. 실명을 내보내는 모든 경로가 그렇게 하고 있다.

- [ ] **Step 1: 실패하는 테스트를 쓴다**

1. `?name=이승호` → 200, `actors` 1건, `status`·`companies` 포함
2. 없는 이름 → **200 + 빈 목록**(404 아님 — 없음은 오류가 아니다)
3. `?name=`과 `?company=` 동시 → **400**
4. 둘 다 없음 → **400**
5. 레지스트리를 못 가져온 상태(`bundled` + opt-in) → **502**, 문구가 "없음"이 아니라 "조회 실패"
6. 응답에 면책 문구가 있다
7. 인증 없으면 401(기존 가드 유지)
8. `status`가 빈 문자열인 기록도 `auto_matched`로 내려간다(`actor_status` 경유 — 동등 비교로 짜면 실패해야 한다)

## Task 2: 임원 명단 ↔ 레지스트리 대조 (순수 로직)

**Files:**

**Interfaces:**

**요구사항:**

- 대조는 **정규화된 표기 일치**만 본다. `lookup_actor`가 서버에서 이미 그 일을 하므로 **클라이언트에서 다시 매칭 규칙을 만들지 마라** — 규칙이 두 벌이 되면 서버와 화면이 다른 답을 낸다.
- 이 회사 자신은 `companies`에서 **제외**한다. "엔켐 임원이 엔켐에 등장"은 정보가 아니다. 회사명 비교는 서버가 쓰는 정규화와 어긋날 수 있으니, **어긋날 때 제외하지 않는 쪽**(정보를 남기는 쪽)으로 실패하게 하고 그 이유를 주석에 남겨라.
- 매칭이 0건인 임원도 결과에 **포함**한다(`registered: false`). 화면이 "대조했고 없었다"와 "대조하지 않았다"를 구분해야 한다.
- 입력이 배열이 아니거나 비면 `{}`.

- [ ] **Step 1: 실패하는 테스트를 쓴다**

픽스처는 **실측 형태 그대로** — 임원 응답 필드(`nm`·`birth_ym`·`ofcps`·`rgist_exctv_at`)와 실측 매칭 사례(`이승호` → `FSN`·`위노바`)를 쓴다.

4. `statuses`에 `auto_matched`가 그대로 실린다(정보를 지우지 않는다)
5. 빈 입력·비배열 입력에 예외가 없다

- **동명이인 판별을 시도하지 않기로 했다(2026-07-29 결정).** 수십~수백 명을 우리가 가려 주는 건 이 도구가 질 부담이 아니고, 생년월도 없어 틀릴 수밖에 없다. 대신 **경고를 실행 가능하게** 만든다 — 확인 방법 세 가지를 화면이 직접 말한다. 이 결정은 기능을 줄이는 게 아니라 **책임의 위치를 정직하게 두는 것**이다.
- **자동 확인이 불가능하다는 것을 실측으로 확인했다** — 임원 응답에는 `birth_ym`이 있지만 레지스트리에는 없다. 이 사실을 숨기지 않고 화면에 적는다.
