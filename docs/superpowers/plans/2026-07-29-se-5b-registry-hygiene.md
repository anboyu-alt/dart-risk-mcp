# SE-5b 행위자 레지스트리 위생 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 반복 등장이 **정상인** 제도권 기관이 "반복 등장 행위자" 상위를 차지해 진짜 세력을 가리는 문제를 없앤다.

**Architecture:** 필터(`should_store`)와 정규화(`normalize_name`)는 **이미 core에 있고 정상 작동한다.** 결함은 읽기 경로가 그것들을 쓰지 않는다는 것이다. `known_actors.py`의 로드·조회 경로에 필터를 걸고, 정규화에 HTML 엔티티 제거를 더한다. **비공개 Notion DB는 건드리지 않는다** — 지울 목록을 보고하는 스크립트만 만들고 실행은 제작자가 한다.

**Tech Stack:** Python(core, 표준 라이브러리만), pytest.

## Global Constraints

- **판정 금지 (v0.8.5).** 레지스트리는 사실 표기다. 이 계획은 무엇이 노이즈인지만 다루고, 남은 인물에 대해 어떤 평가·점수·순위도 만들지 않는다.
- **제작자의 비공개 Notion DB를 수정하지 않는다.** 삭제는 되돌리기 어렵고 외부에 영향을 준다. 스크립트는 **보고만** 한다.
- **사람이 일부러 넣은 등재를 지우지 않는다.** 읽기 필터는 `auto_matched`(기계 등재)에만 적용한다. `verified`·`maintainer_seed`는 그대로 통과시킨다 — 제작자가 판단해 넣은 것이기 때문이다.
- **`dart_risk_mcp/` 변경이 MCP 도구 26개에 미치는 영향을 명시한다.** 이 계획은 `lookup_known_actor`·`find_actor_overlap`·`analyze_company_risk`·`build_event_timeline`의 출력을 **의도적으로** 바꾼다(노이즈 제거). 그 외 도구는 영향이 없어야 한다.
- **외부 의존성 추가 금지.**
- **레지스트리 미설정 시 동작을 바꾸지 않는다.** Notion 자격증명이 없으면 지금처럼 조용히 빈 레지스트리로 동작해야 한다.

### 결함 2 — 같은 실체가 레지스트리에 **두 개의 키**로 남아 있다

> **⚠️ 정정(2026-07-29):** 이 절은 원래 "`normalize_name`이 HTML 엔티티를 남긴다"고 적혀 있었다. **틀렸다.** `normalize_name`은 `strip_role_qualifier`를 통해 이미 엔티티를 제거한다(커밋 `f64caca`). 계획 작성자가 레지스트리 원본 키에 `&CR;`가 보이는 것을 보고 정규화가 안 된다고 결론냈는데, **바로 자기가 출력한 "중복 키 3쌍"이 정규화가 작동한다는 증거였다.** 실제 결함은 아래와 같이 한 단계 뒤에 있다.

원문 파싱에서 `&CR;`가 새어 들어와 레지스트리에 **두 개의 키**로 저장됐다. 실측 4건:

```
SBI-KIS 2018 투자조합&CR;업무집행조합원 SBI인베스트먼트
미래에셋대우 주식회사&CR;(지브이에이 FORTRESS-A ...)
삼성전자 &CR;주식회사
케이파트너스&CR;주식회사
```

`normalize_name`은 이 둘을 같은 값으로 만든다. **그런데 `lookup_actor`는 정확 키 일치를 먼저 시도하고 거기서 반환해 버려, 나머지 키의 기록을 보지 못한다.** 실측:

| 조회 표기 | 반환 기록 수 |
|---|---:|
| `삼성전자 주식회사` | **1건** |
| `삼성전자 &CR;주식회사` | **2건** |
| `SBI-KIS 2018 투자조합 업무집행조합원 SBI인베스트먼트` | **1건** |
| `SBI-KIS 2018 투자조합&CR;업무집행조합원 SBI인베스트먼트` | **2건** |

같은 실체인데 **어떤 표기로 묻느냐에 따라 답이 달라진다.**

**영향 범위는 작다 — 정직하게 적는다.** 이 2쌍에서 두 키의 `companies` 집합은 우연히 같아(4개=4개, 2개=2개) 등장 회사 수는 달라지지 않는다. 잃는 것은 `evidence`·`rcept_no` 같은 근거 기록이다. 그래도 "같은 사람을 둘로 세지 않는다"는 이 도구의 전제에 어긋나므로 고친다.

**관련기업 태그(`companies`)에는 엔티티가 0건이다** — 인물명에만 있다.

### 이미 있어서 만들지 않는 것

- `should_store`(`known_actors.py:350`) — 정상 작동. **재구현 금지.**
- `normalize_name`(`known_actors.py:116`) — 역할 괄호 제거·공백 단일화·대문자 통일이 이미 있다. 엔티티 제거만 더한다.
- `_INSTITUTION_PAT`(`:249`)·`classify_actor`·`sector_of` — 손대지 않는다.

## Self-Review 결과

- **가장 큰 위험은 과잉 삭제**다. 필터는 `should_store`가 거부 + 전 기록이 기계 등재, 두 조건을 모두 만족할 때만 작동한다. Task 2의 검증 3·5·8번이 그것만 노린다.
- **두 번째 위험은 빈 status**다. 같은 저장소에서 Notion 파서가 `status: ""`를 내보내 미검증 실명이 검증된 것처럼 표시된 사고가 있었다. 화이트리스트로 처리하고 검증 4번으로 고정한다.
- **Notion을 건드리지 않는다.** 제작자의 비공개 자산이고 삭제는 되돌리기 어렵다. 읽기 필터로 화면·도구 출력을 즉시 고치고, 실제 정리는 보고서를 보고 제작자가 결정한다.
- **13.7초 콜드 로드는 이 계획의 범위 밖이다.** Vercel 파일시스템이 휘발이라 매 콜드 호출마다 Notion을 왕복한다. SE-1이 만든 Supabase 캐시에 레지스트리를 물리는 것이 해법이며 별도 계획으로 다룬다.
