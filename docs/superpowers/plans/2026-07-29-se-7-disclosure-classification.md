# SE-7 공시 분류 확대 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 공시 목록 색상 구분이 회사에 따라 76~98%가 "기타"로 뭉개지는 것을 고친다. **세 개의 서로 다른 원인**이 있고 각각 다르게 고친다 — 하나로 뭉뚱그리지 않는다.

**Architecture:**
1. **core 키워드 누락 수정** (`dart_risk_mcp/core/signals.py`) — `DISCLOSURE_VIOL`에 DART 실제 공식 용어가 빠져 있다. MCP 26개 도구도 이득을 본다.
2. **SE 표시 계층의 재사용 오류 수정** (`docs/tool/se/app.js`) — 정정공시 전 배제는 위험 신호 **집계**를 위한 설계인데, SE가 그걸 **전체 목록 색칠**에 그대로 재사용해 정정공시가 전부 "기타"로 떨어진다.
3. **SE에 새 중립 범주 추가** — 고빈도 정기 보고(임원 지분보고 등)는 위험 신호가 아니라서 "기타"에 안 걸리는 게 **맞다.** 다만 "기타"(모르는 것)와 "정기 보고"(아는데 위험 신호가 아닌 것)는 다른 사실이라 구분해서 말한다.

**Tech Stack:** Python(core, 표준 라이브러리만), 순수 ES5 스타일 JS, pytest + node 서브프로세스.

## Global Constraints

- **판정 금지 (v0.8.5).** 새 범주("정기 보고" 등)는 **사실 라벨**이지 위험 등급이 아니다. "안전"·"위험 없음"으로 읽히는 이름을 쓰지 않는다.
- **core `SIGNAL_TYPES`에 정기 보고 유형을 넣지 않는다.** 위험 신호 8분류(1~8)와 "정기 보고"는 다른 층위다. 섞으면 위험 신호 집계(`calculate_risk_score` 등)가 오염된다. 정기 보고 목록은 **SE 표시 전용**으로 별도 관리한다.
- **`match_signals`(core)의 정정공시 배제 동작을 바꾸지 않는다.** 그 함수는 위험 신호 집계용으로 이미 옳다(`analyze_company_risk` 등 여러 MCP 도구가 이 동작에 의존한다). 표시 계층에서 다르게 쓰는 새 로직을 만든다 — 기존 함수를 고치지 않는다.
- **`dart_risk_mcp/` 키워드 추가는 골든 출력에 영향을 줄 수 있다.** `tests/fixtures/sample_outputs/`에 `불성실공시`가 들어간 골든이 있으면 기대값이 왜 바뀌는지 커밋 메시지에 적고 갱신한다.
- **DOM 주입 금지.** 데이터는 `textContent`로만.
- **외부 의존성 추가 금지.**

### 원인 1 — core 키워드 누락 (진짜 위험 신호 놓침)

엔켐 "기타" 안에 `불성실공시법인지정`·`불성실공시법인지정예고`가 있다. `DISCLOSURE_VIOL`(`signals.py`) 키워드는 `['공시의무위반', '공시누락', '중요정보누락', '발행철회', '공시철회']`인데, **DART가 실제로 쓰는 공식 용어는 `불성실공시법인`이다.** 실측 확인:

```python
match_signals("불성실공시법인지정") == []   # 놓침
```

**이건 SE만의 문제가 아니다.** `match_signals`는 core 함수라 `analyze_company_risk`·`search_market_disclosures(preset="audit_issue")`·`build_event_timeline` 등 이 키워드에 기대는 모든 MCP 도구가 같은 구멍을 갖고 있다.

### 원인 2 — 정정공시 전 배제를 "전체 목록 색칠"에 잘못 재사용

`match_signals`(core, `signals.py:600`):

```python
def match_signals(report_nm: str) -> list[dict]:
    """... 정정공시([기재정정] 등)는 새 공시가 아니므로 빈 리스트를 반환한다."""
    if is_amendment_disclosure(report_nm):
        return []
    ...
```

이건 **위험 신호 집계**에서 같은 사건의 정정본을 중복 계산하지 않으려는 의도적 설계다. **옳다.**

문제는 SE의 `classifyDisclosureCategory`(`app.js:2302`)가 `signals-data.json`의 `amendment_pattern`으로 **같은 배제**를 그대로 복제해 놓고, 이걸 "이번 달 공시가 무슨 색이었나" 전체 목록 색칠에 쓴다는 것이다. **정정공시는 내용과 무관하게 무조건 색이 없다.**

실측 — 정정 접두어를 벗기고 재매칭하면:

| 회사 | 기타 | 정정이라 빠진 것 | 벗기고 재매칭 시 회복 | 회복 후 기타 |
|---|---:|---:|---:|---:|
| 엔켐 | 110건 | 61건 | **40건** | 70건(49%) |
| 삼성전자 | 982건 | 26건 | 0건 | 982건(98%, 원인 3 때문) |

엔켐은 정정공시 배제가 원인의 상당 부분이다(76%→49%). 삼성전자는 이 원인의 영향이 0건이다 — 원인 3이 지배적이기 때문이다.

**⚠️ `_AMENDMENT_RE`는 접두어 전용 정규식이라 안전하게 벗길 수 있다:**
```python
_AMENDMENT_RE = re.compile(r"^\[(?:기재정정|첨부추가|정정)[^\]]*\]\s*")
```
`.sub("", text)`로 벗기면 나머지 제목이 그대로 남는다(중간에 잘리지 않는다).

### 원인 3 — 고빈도 정기 보고가 "기타"를 지배한다 (이건 결함이 아니라 사실이다)

삼성전자 "기타" 982건 중 **924건(94%)이 정확히 한 유형**이다:

```

[기재정정]임원ㆍ주요주주특정증권등소유상황보고서   16건
```

이건 임원 개개인이 지분이 1주만 바뀌어도 각자 내는 **정기 보고**다. **위험 신호가 아닌 게 맞다** — `insider_timeline` 섹션이 이미 이 데이터를 별도로 다룬다(`elestock`/`hyslrSttus` 기반, SE-6에서 다룬 그 데이터다). 이걸 8개 위험 신호 카테고리 중 하나로 강제로 우겨넣으면 그게 판정이 된다.

**그런데 "기타"라는 이름이 거짓말을 한다.** "기타"는 "우리가 뭔지 모른다"로 읽히는데, 사실은 **뭔지 알고 있고 위험 신호가 아니라고 판단한 게 아니라 애초에 그 범주가 아니다.** "모른다"와 "안다, 정기 보고다"는 다른 사실이다.

**남는 진짜 목록(양쪽 회사, 정정 배제 재원인·정기보고 재원인 제거 후):**

| 유형 | 건수(엔켐) | 유형 | 건수(삼성전자) |
|---|---:|---|---:|
| 타법인주식및출자증권취득/처분결정 | 14 | 최대주주등소유주식변동신고서 | 11 |
| 임원·주요주주소유상황보고서 | 12 | 동일인등출자계열회사와의상품·용역거래변경 | 6 |

**정기 보고로 분류할 후보(사업보고서류·주총 소집·기업설명회):** 정례적으로 나오고 위험 신호가 아니다.

## Task 2: SE — 정정공시를 "제외"가 아니라 "사실 표기"로 재분류

**Files:**
- Modify: `docs/tool/se/app.js`
- Test: `tests/se/test_se_app_js.py`

**Interfaces:**
- Consumes: `signalsData.amendment_pattern`(이미 있음), `signalsData.signals[].keywords`
- Modifies: `classifyDisclosureCategory(reportNm, signalsData)`

**요구사항 — 이 태스크가 하는 일은 정확히 하나다: 정정 접두어를 벗기고 그 뒤로 매칭한다**

- 지금: `amendment_pattern`에 걸리면 **즉시 category 0을 반환**한다(`app.js:2305~2312`).
- 바꿀 것: `amendment_pattern`에 걸리면 **접두어를 제거한 나머지 텍스트로 키워드 매칭을 계속한다.** 매칭되면 그 카테고리, 안 되면 0(기타).
- **정정 여부 자체는 사실로 남긴다** — 반환값에 `is_amendment` 플래그를 추가한다(카테고리 숫자만 반환하던 것을 `{category, isAmendment}` 객체로 바꾸거나, 별도 함수를 하나 더 두거나 — 호출부(`monthlyCountsByCategory` 등)가 지금 숫자만 쓰고 있다면 **그 계약을 깨지 않는 선택**을 하라. 숫자 반환은 그대로 두고 정정 여부가 필요한 화면(범례·툴팁)만 별도로 `isAmendmentDisclosure(reportNm, signalsData)`를 새로 만들어 부르는 편이 더 안전할 수 있다. 어느 쪽을 택했는지 이유를 코드 주석에 남겨라).
- **정규식을 `.replace()`로 재사용할 때 앵커가 접두어 전용인지 확인한다.** `amendment_pattern`이 `^\[...\]\s*` 형태(문자열 시작 고정)임을 실측으로 확인했다 — 문자열 어디서든 걸리는 패턴이면 본문 중간을 잘못 잘라낼 수 있으니, 만약 다른 패턴이 들어온다면 `^`로 시작하는지 확인 후에만 `.replace()`를 적용하고, 아니면 원본 그대로 매칭한다.
- **`is_amendment_disclosure`(core)의 동작 자체는 안 건드린다** — 위험 집계용 배제는 그대로 유지. 이 태스크는 오직 `app.js`(SE 표시 계층)만 건드린다.

- [ ] **Step 1: 실패하는 테스트를 쓴다**

픽스처는 **실측 값 그대로**(`signals-data.json`의 실제 `amendment_pattern`과 CB_BW 키워드 사용).

1. `classifyDisclosureCategory("주요사항보고서(전환사채권발행결정)", data)` → CB_BW의 category(실측: 1)
2. `classifyDisclosureCategory("[기재정정]주요사항보고서(전환사채권발행결정)", data)` → **같은 category(1)** — 지금은 0이 나온다, 이게 이 태스크가 고치는 결함이다
3. `classifyDisclosureCategory("[기재정정]불성실공시법인지정", data)` → Task 1이 추가한 키워드로 매칭되면 그 category(core와 signals-data.json 양쪽에 키워드가 있어야 하므로, 이 테스트는 Task 1 완료 후 실행 가능 — 순서를 지켜라)
4. 정정 접두어를 벗겨도 매칭되는 게 없으면 → 0(기타). "정정이라 매칭 안 됨"과 "내용상 매칭 안 됨"이 최종적으로 같은 0이어도, 그 과정에서 내용까지 본 것이 이 태스크의 핵심이다
5. `amendment_pattern`이 없거나 깨진 정규식이어도 예외 없이 기존처럼 동작한다(기존 방어 유지)
