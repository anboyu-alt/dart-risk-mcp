# 행위자 연결망 동일 실체 중복 노드 해소 계획 (에이프로젠 사례)

- 날짜: 2026-08-03
- 상태: 계획 수립 완료 — 구현 미착수 (사용자 지시: "구현은 나중에")
- 발단: 연결망 HTML 검색창에 '에이프로젠' 입력 시 회사 2건 + 법인 5건이 따로 나열됨.
  사용자 질문 — "이 법인·회사들 결국 다 같은 곳 아닌가?"

분리 유지가 맞다(계열 간 자금 흐름을 보는 게 연결망의 목적이므로 오히려 정보다).
비상장 00549059는 진짜 동명 별개 법인이라 노드 분리는 맞지만 **화면에서 구분 표기가
없어** 같은 이름이 두 번 보이는 혼란을 만든다.

## 2. 근본 원인 4가지

**A. fold 충돌 시 병합 전면 포기** — `build_network_html.build_graph`의 `fold2cc`는
한 fold가 corp_code 1개일 때만 병합한다(모호 가드). fold `'에이프로젠'`이
{00152385, 00549059} 2개에 걸리자 `(주)에이프로젠` 행위자의 회사 병합까지 통째로
포기돼 3분열(회사 2 + 행위자 1)이 생겼다. 같은 충돌이 전체 12건
(코스텍시스·카이노스메드·자비스·원텍·휴럼 등 — 대부분 상장사+동명 비상장 조합).

**B. self-heal 산출물 미소비** — discover_actors의 `reconcile_corp_renames`
(2026-07-23 도입)는 법인 행위자 키를 corp_code로 해석해 `actor_corp_ids`·`aliases`로
영속화한다. 실제로 `(주)에이프로젠`은 00152385로 해석 가능하다. 그러나
`build_network_html`은 이 맵을 읽지 않고 자체 fold 재유도만 한다 — A의 모호 가드에
걸리면 이미 확보된 해석 결과도 버려진다.

**C. 옛 상호 백필 창 부족** — `backfill_renames.py` 기본 창이 3년(2023~)이라
2020-03의 에이프로젠KIC→MED 개명이 `corp_renames`에 없다. `(주)에이프로젠케이아이씨`
(2018~19 레코드)는 현재 명부에도, legacy 맵에도 없어 해석 불가로 남는다.

**D. 스냅샷 신선도** — 사용자의 network.html은 2026-07-20 빌드로, 7-23 self-heal
도입 이전 sightings 기준이다(`actor_corp_ids`·`corp_renames` 필드 자체가 없음 —
로컬 tmp/sightings.json 실측). `(주)앱토크롬(舊. ㈜에이프로젠헬스케어앤게임즈)`류
병기 표기 별칭 병합(`fold_variants`)도 미반영 상태다.

부수 관찰(참고): `reconcile_corp_renames`의 `_corp_name_index`는 이름 키 dict
(`_corp_cache`)를 쓰므로 동명 법인 중 상장사만 남아 `'에이프로젠'` fold가 **우연히**
비모호(00152385 단독)로 해석된다. 결과는 옳지만 이는 `_merge_corp_entry`의 상장 우선
정책에 암묵적으로 기댄 것 — 계획 4에서 명시적 정책으로 승격한다.

## 3. 수정 계획 (구현 순서)

### Task 0 — 베이스라인 재검증 (코드 변경 없음)
private repo(dart-risk-mcp-sightings)의 최신 sightings로 network.html을 재생성해
7-23 self-heal이 이미 접는 항목(병기 표기·최근 개명)을 확인하고, 잔존 중복 목록을
확정한다. → 이후 Task들의 효과 측정 기준점.

### Task 1 — build_network_html이 `actor_corp_ids`를 1순위로 소비
`canon_actor_id`에서 sightings의 `actor_corp_ids` 역맵(정본 행위자 키 → corp_code)을
먼저 조회하고, 없을 때만 기존 `fold2cc` 폴백. 별칭(`aliases`)으로 정본에 합류한 키도
역맵을 타므로 `(주)에이프로젠` → `c:00152385` 병합이 fold 충돌과 무관하게 성립한다.
기존 self-loop 가드·병합 시 원표기 aliases 보존 로직은 그대로 유지.
- 단위 테스트: 동명 2 corp_code + actor_corp_ids가 있는 픽스처에서 3분열이
  이중역할 노드 1개 + 동명 회사 노드 1개로 줄어드는지 (`tests/test_build_network_html.py`).

### Task 2 — 옛 상호 백필 창 확대 (운영 1회 실행)
`backfill_renames.py --start 2015-01-01` 1회 실행(private repo, 운영자 작업)으로
2015~2023 상호변경안내를 `corp_renames`에 소급 축적. 이후
`reconcile_corp_renames`가 `(주)에이프로젠케이아이씨` → 00152385 별칭을 자동 등록,
Task 1의 역맵을 타고 회사 노드로 접힌다. 코드 변경 없음 — 실행 비용(공시 원문 조회
수)만 산정해 cron이 아닌 수동 1회로 처리.

### Task 3 — 동명 별개 법인의 화면 구분 (network_template.html)
진짜 동명 이법인(00549059류)은 병합하면 안 되므로 **구분 표기**로 해소한다:
- 검색 리스트: 회사 노드에 시장 배지(KOSPI/KOSDAQ/KONEX/비상장)를 항상 병기,
  상장사는 종목코드도 표기 (데이터는 이미 노드에 있음 — `mkt`).
- 같은 라벨의 노드가 2개 이상이면 상세 패널에 "동명 별개 법인 N건 — corp_code 기준
  구분" 사실 주석 1줄 표시 (판정 없음 원칙 유지: 합병·계열 관계 추정은 하지 않는다).

### Task 4 — `_corp_name_index`의 동명 처리 명시화 (defensive)
이름 키 dict 우연 의존을 제거: fold → corp_code 집합을 원본 명부 전체 기준으로 만들되,
충돌 시 `_merge_corp_entry`와 동일한 **상장 우선** 티브레이크를 명시 적용하고, 동급
충돌(둘 다 상장/둘 다 비상장)만 모호로 남긴다. 현재 통과 사례(에이프로젠)의 동작은
불변, 상장+비상장 충돌 12건 중 유사 케이스의 해석이 정책 문서화된 형태로 안정된다.
- 리스크: 비상장 동명 법인이 실제 행위자인 경우의 오귀속 가능성 → 별칭 등록 시
  근거(`resolved_by: "listed-tiebreak"` 등) 필드를 남겨 추적 가능하게 한다.

### Task 5 — 문서·검증
- CLAUDE.md 연결망 절에 병합 우선순위(actor_corp_ids > fold2cc > 미병합) 1줄 반영.
- 에이프로젠 시나리오 종단 확인: 재생성 HTML에서 검색 '에이프로젠' 결과가
  [에이프로젠(KOSPI·이중역할, 별칭에 (주)에이프로젠·케이아이씨 표시),
  에이프로젠(비상장), 바이오로직스(KOSPI), 아이앤씨, 파마] 5건으로 수렴하는지.

## 4. 비범위 (이번 계획에서 하지 않는 것)
- **합병 계보 자동 병합**(00549059 → 00152385): 흡수합병 이력을 DART에서 추적해
  회사 노드를 접는 기능은 별도 데이터 소스(합병 결정 공시 파싱)가 필요하고,
  "판정 없음" 원칙과의 경계가 미묘해 보류. Task 3의 사실 주석으로 대체.
- **그룹(계열) 클러스터링**: '에이프로젠*' 접두 유사성 기반 묶음은 판정이므로 안 함.
  계열 여부는 이미 엣지(누가 누구에 돈을 댔나)가 사실로 보여준다.
- `classify_actor`의 bare 이름 person 오분류(예: '에이프로젠 H&G' → person):
  화면 영향 경미(회사 노드는 type=company로 덮임) — 별도 이슈로만 기록.
