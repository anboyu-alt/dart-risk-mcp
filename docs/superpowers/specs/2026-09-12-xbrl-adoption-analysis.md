# XBRL 전체 태그 도입 — 실측 기반 타당성 분석

측정일 2026-09-12 · `fnlttXbrl.xml`을 12개사에 대해 실제로 받아 해부한 기록.

> ⚠ **이 문서는 같은 날 한 번 정정됐다.** 1판은 "계정명 대조 소스를 감사보고서에서
> XBRL로 바꾸자"를 권고했다. 맥락 축(`contextRef`)으로 좁혀 다시 재니 **그 권고가
> 틀렸다** — API가 이미 XBRL 라벨을 그대로 주고 있었고, 근거로 들었던 반례도
> 해석이 틀렸다. 아래 §2가 정정 내용이고, 틀린 판단은 §6에 남겨 둔다.

> ⚠ **선행 조사가 있었는데 근거가 사라졌다.** `dart_client.py:4950`에
> *"전면 XBRL 파싱(택소노미 계층)은 비채택 — tmp/xbrl_feasibility/REPORT.md B안"*
> 이라는 주석만 남아 있고, 그 리포트는 `tmp/`라 **커밋되지 않았다**. 그래서 처음부터
> 다시 쟀다. **결론은 그 주석과 같다** — 옛 판단이 옳았다.

---

## 0. 결론

**도입하지 않는다.** `fnlttSinglAcntAll`이 이미 XBRL 인스턴스의 **충실한 투영**이라,
XBRL을 직접 파싱해도 **같은 이름·같은 축을 다시 얻을 뿐**이다.

| 기대했던 이득 | 실측 결과 |
|---|---|
| ① 회사 원문 계정명을 얻는다 | ❌ **API 계정명 = XBRL 라벨. 47개사 18,126행 전수 대조 — 불일치 0건** |
| ② 자본변동표(SCE) 열을 안다 | ❌ **API `account_detail`이 이미 100% 준다** |
| ③ 「파생상품평가손익」 사고를 고친다 | ❌ **회사 XBRL도 그렇게 태깅돼 있다** — API가 틀린 게 아니었다 |
| ④ 주석이 숫자로 태깅돼 있다 | ⚠️ 사실이나 **회사별 편차 135배** — 전제로 쓸 수 없다 |

남는 유일한 미개척지는 ④인데, 편차가 커서 "있으면 쓰고 없으면 만다"밖에 안 된다.
비용(코아스 한 건 해제 **87MB** · fact **36,655개**)에 견주면 사지 않는 게 맞다.

## 1. 무엇을 재었나

`fnlttXbrl.xml`(사업보고서 XBRL 원본 ZIP)을 12개사 2025 사업연도에 대해 받아
`fnlttSinglAcntAll.json`(지금 쓰는 것)과 대조했다.

| 회사 | ZIP | 해제 | fact | 고유요소 | 회사 확장요소 |
|---|---:|---:|---:|---:|---:|
| CSA 코스믹 | 120 KB | 2.3 MB | 1,342 | 222 | 76 |
| STX | 755 KB | 16.6 MB | 6,043 | 628 | 138 |
| 삼성전자 | 802 KB | 19.3 MB | 5,420 | 625 | 161 |
| KR모터스 | 932 KB | 22.9 MB | 8,128 | 686 | 223 |
| **코아스** | **2.6 MB** | **87.1 MB** | **36,655** | 936 | 279 |

ZIP 구성은 7개 파일로 일정하다 — 인스턴스(`.xbrl`) · 스키마(`.xsd`) ·
**한글 라벨**(`lab-ko`) · 영문 라벨 · 표시(`pre`) · 계산(`cal`) · 정의(`def`).

**대조 방법**: XBRL `context`를 `{기간유형, 시점·종료일, 축→멤버}`로 파싱하고,
API 행의 `(fs_div, sj_div)`로 후보 맥락을 좁힌 뒤 금액으로 되짚어 라벨을 비교했다.

- BS → `instant`, 추가 축 없음
- IS/CIS/CF → `duration`, 추가 축 없음
- SCE → `duration` + `ComponentsOfEquityAxis` 보유
- 연결/별도는 `ConsolidatedAndSeparateFinancialStatementsAxis`로 가름

## 2. 결과 — 기대한 이득이 전부 없었다

### 2-1. API 계정명은 이미 XBRL 라벨이다 — 47개사 전수, 불일치 0건

> 「계정명은 절대 틀리면 안 된다」는 요구에 맞춰 표본을 12 → **47개사**로 늘리고,
> **서로 독립인 두 방법**으로 따로 쟀다. 표본은 레포의 측정 표본 명부
> (`tests/fixtures/samples/measurement_cohorts.json` 50곳) + CSA 코스믹.

**M1 — 요소 정확 대조** (모호함이 원리적으로 없다)

API가 스스로 밝힌 `account_id`의 XBRL 한글 라벨과 `account_nm`을 견준다.
"API 이름이 그 요소의 라벨인가?"

```
47개사 19,786행
  같음        18,126   91.6%
  다름             0    0.0%     ◀ 전수 0건
  account_id 없음  1,660    8.4%   (API가 '-표준계정코드 미사용-'을 준 행)
  라벨 없음         0    0.0%
  ▶ 대조 가능 18,126행 중 다름 0행 — 0.000%
```

**M2 — 금액 + 맥락 대조** (기간 축을 인스턴스에서 복원해 실제로 걸었다)

```
대조 대상 14,601행
  같음   13,257   90.80%
  다름      119    0.82%
  모호       16    0.11%
  못찾음   1,209    8.28%
```

| | 행 | 같음 | **다름** | 모호 | 못찾음 |
|---|---:|---:|---:|---:|---:|
| BS | 4,183 | 99.8% | **0.00%** | 0.00% | 0.2% |
| IS | 414 | 99.5% | **0.00%** | 0.00% | 0.5% |
| CIS | 1,953 | 98.3% | **0.00%** | 0.10% | 1.6% |
| CF | 3,956 | 95.2% | **0.00%** | 0.00% | 4.8% |
| **SCE** | 4,095 | 72.9% | **2.91%** | 0.34% | 23.9% |

**본표 네 종류(BS·IS·CIS·CF)는 다름이 정확히 0이다.** 119건 전부가 SCE다.

### 2-1b. 그 119건은 API 오류가 아니다 — 교차 확인

M2가 「다름」이라 부른 행을 M1으로 되짚었다. **표본 25건 전부 M1 「같음」**이다:

```
삼성전자 SCE  API '자본총계' (897,514,000,000)
   account_id          : ifrs-full_Equity
   그 요소의 XBRL 라벨 : ['기말자본', '기초자본', '자본', '자본총계']   ← API 이름이 여기 있다 ✓
   내가 M2에서 집어온 것: '기초자본'  ← dart_EquityAtBeginningOfPeriod (다른 요소, 금액만 같다)

KR모터스 SCE  API '주식발행비' (67,001,550)
   account_id          : ifrs-full_PaymentsForShareIssueCosts
   그 요소의 XBRL 라벨 : ['주식발행비', '주식발행비 현금흐름']            ✓
   내가 M2에서 집어온 것: '주식발행초과금의결손금보전'
                         ← dart_TransferFromSharePremiumToAccumulatedDeficit

고려아연 SCE  API '종속기업 취득' (-5,097,957,696)
   account_id          : ifrs-full_IncreaseDecreaseThroughAcquisitionOfSubsidiary
   그 요소의 XBRL 라벨 : ['종속기업 취득', '종속기업의 취득으로 인한 증가(감소), 자본']  ✓
   내가 M2에서 집어온 것: '종속기업 유상증자' ← entity00102858_… (회사 확장요소)
```

⚠ **원인은 자본변동표의 구조다.** SCE는 같은 금액이 여러 행에 나타난다
(한 열의 「기초자본」이 다른 행의 「자본총계」와 같은 수다). 금액으로 되짚으면
엉뚱한 요소가 걸리는데, **M1은 요소를 직접 지목하므로 그 충돌이 없다.**
SCE의 「못찾음 23.9%」도 같은 뿌리다 — 기초/기말 시점이 FY 필터에 걸러진다.

⇒ **두 방법이 어긋나는 자리에서 옳은 쪽은 M1이고, M1의 답은 불일치 0이다.**

### 2-1c. 이 결과가 보장하는 것과 보장하지 않는 것

| | |
|---|---|
| ✅ **보장한다** | API `account_nm`은 **회사가 XBRL에 붙인 한글 라벨** 그대로다. 47개사 18,126행에 예외가 없다. 우리 도구가 API 이름을 그대로 찍는 한 **XBRL 기준으로는 틀릴 수 없다** |
| ❌ **보장하지 않는다** | 그 이름이 **회사가 인쇄한 감사보고서의 표기와 같다**는 것. §2-2가 그 반례이고, 2026-09-12 실측으로 **15.7%가 다르다** |

즉 **「계정명이 틀린다」는 위험은 API↔XBRL 축이 아니라 API↔인쇄물 축에만 있다.**
그 축은 XBRL로 못 막는다(§2-2). 현행 감사보고서 대조가 그 자리를 지키는 유일한 장치다.

### 2-1d. 검증에서 제외된 4곳

| 회사 | 사유 |
|---|---|
| **KT&G** | ⚠ **`resolve_corp("KT&G")`가 `None`을 돌려준다.** `"케이티앤지"`·`"033780"`은 정상 해석된다 — DART 명부의 정식 명칭이 「케이티앤지」이고 브랜드 표기가 명부에 없다. **XBRL과 무관한 별개 결함**이라 따로 남긴다 |
| 다산네트웍스 · 포승그린파워 · 포시에스 | 2025 사업보고서가 조회 창에 없음 |

### 2-2. ⚠ 「파생상품평가손익」 사고는 XBRL도 못 고친다 — 1판의 오독 정정

2026-09-12에 기록한 사고 — CSA 코스믹 2025 연결에서 API는
`파생상품평가손익 -8,969,358`인데 감사보고서 원문은 **`지분법자본변동`**이었다.

1판은 그 금액을 XBRL에서 찾아 `entity00406037:ChangesInEquityCapital…` / 라벨
**`지분법자본변동`**을 발견하고 *"XBRL이 원문 이름을 갖고 있다"*고 적었다.
**그건 맥락을 안 본 것이다.** 같은 값을 가진 fact를 축까지 찍으면:

```
· entity00406037:ChangesInEquityCapitalOfStatementOfChangesInEquityLineItems
    라벨 '지분법자본변동'   축 {연결, ComponentsOfEquityAxis: 기타자본구성요소}      ← 자본변동표
· entity00406037:ChangesInEquityCapitalOfStatementOfChangesInEquityLineItems
    라벨 '지분법자본변동'   축 {연결, ComponentsOfEquityAxis: 지배주주지분}          ← 자본변동표
· entity00406037:ChangesInEquityCapitalOfStatementOfChangesInEquityLineItems
    라벨 '지분법자본변동'   축 {연결}                                              ← 자본변동표 합계
· ifrs-full:GainsLossesOnChangeInValueOfTimeValueOfOptionsNetOfTax
    라벨 '파생상품평가손익'  축 {연결}                                              ← 포괄손익계산서
```

**회사가 포괄손익계산서 줄을 직접 그 표준 태그로 달았다.** API는 회사의 XBRL을
충실히 옮긴 것이고, 어긋나는 것은 **회사의 XBRL 태깅 ↔ 회사가 인쇄한 감사보고서**다.

⇒ 감사보고서는 **XBRL이 대체할 수 없는 별개의 원천**이다. 두 소스는 서로 다른 질문에 답한다.

| | 답하는 질문 |
|---|---|
| API·XBRL | 회사가 **무엇으로 태깅했나** |
| 감사보고서 | 회사가 **무엇으로 인쇄했나** |

기사에 옮기는 것은 **인쇄된 표기**이므로, `get_financial_statements_full`의 현행
감사보고서 대조는 **그대로 두는 것이 맞다**.

### 2-3. 자본변동표 열도 API가 이미 준다

CLAUDE.md에 *"SCE는 계정명이 행이 아니라 열에 있다"*고 적어 둔 문제를 XBRL의
`ComponentsOfEquityAxis`가 푼다고 봤는데, **API `account_detail`이 그 축을 이미
문자열로 준다**. 3개사 SCE 404행 전수 확인 — **100% 채워져 있다**.

```
'자본 [구성요소]|지배기업의 소유주에게 귀속되는 지분 [구성요소]|이익잉여금 [구성요소]'
'자본 [구성요소]|비지배지분 [구성요소]'
'연결재무제표 [member]'
```

**우리가 이 필드를 안 읽고 있었을 뿐이다.** XBRL을 받을 이유가 아니라,
`account_detail`을 읽으면 되는 일이다.

| 회사 | 총 fact | 주석계열 | 비중 | 특수관계자 | 퇴직급여 할인율 | 리스 |
|---|---:|---:|---:|---:|---:|---:|
| CSA 코스믹 | 1,342 | 138 | 10.3% | 0 | 0 | 0 |
| 삼성전자 | 5,420 | 809 | 14.9% | 812 | 6 | 20 |

## 3. 치러야 할 비용 (도입했다면)

### 3-1. 해제 크기가 가드를 통과한다

ZIP 자체는 **0.4~0.5초 · 0.1~2.6MB**로 싸다. 문제는 해제 크기다.

```
코아스  ZIP 2.6MB → 해제 87.1MB · 최대 단일 항목 52.9MB
```

현재 가드는 이것을 **막지 못한다**:

```
_ZIP_MAX_ENTRIES    = 5,000
_ZIP_MAX_ENTRY_SIZE = 104,857,600  (100MB)  ← 52.9MB 통과
_ZIP_MAX_TOTAL_SIZE = 209,715,200  (200MB)  ← 87.1MB 통과
```

`_is_zip_safe`는 측정한 회사 전부 `True`를 돌려준다. MCP 서버는 사용자 PC에서
도는 것이 전제라, 도입했다면 **XBRL 전용의 더 낮은 상한**이 함께 가야 했다.

> ℹ️ 현행 `extract_xbrl_depreciation`은 인스턴스 하나만 읽어 우연히 비켜 가고 있다.
> **도입하지 않기로 했으므로 이 상한은 지금 손대지 않는다** — 다만 나중에 XBRL
> 용도를 늘린다면 이 줄을 먼저 읽어야 한다.

### 3-2. 회사 확장요소는 일반화가 안 된다

`entity00406037:` 같은 회사 전용 요소가 **76~279종**이고 회사마다 이름이 다르다.
"이 태그는 매출이다"를 코드에 적을 수 없다. 옛 「B안 비채택」의 진짜 이유가
이것일 가능성이 높고, 그 판단은 지금도 유효하다.

### 3-3. 새 의존성은 필요 없었다

이미 `parse_xbrl_depreciation`이 regex로 인스턴스를 읽는다. 이번 측정도 전부
`re` + `zipfile` + `requests`로 했다 — 의존성은 **도입을 막는 이유가 아니었다**.
막은 것은 **얻을 것이 없다는 사실**이다.

## 4. 그래서 할 일

### 채택 — `account_detail`을 읽는다 (XBRL과 무관)

이번 측정의 **유일한 실행 가능 산출물**이다. SCE 404행에서 100% 채워져 오는
자본 열 정보를 우리가 버리고 있다. `get_financial_statements_full`의 SCE 행에
이 값을 병기하면, CLAUDE.md가 적어 둔 *"SCE 대조율 28.4%"* 문제의 상당 부분이
**추가 API 호출 0회로** 풀린다.

⚠ 다만 **감사보고서 대조는 그대로 둔다** — §2-2대로 두 소스는 다른 질문에 답한다.

### 비채택 — XBRL 전면 파싱 · 계정명 소스 교체 · SCE 축

얻을 것이 없다(§2-1·2-2·2-3). 옛 주석의 판단이 옳았다.

### 보류 — 주석 태깅(§2-4)

편차 135배. 필요가 구체적으로 생기면(예: 특수관계자 이자율을 원문 정규식 대신
구조화 값으로 받고 싶을 때) **그때 커버리지를 먼저 재고** 판단한다.

### 미측정으로 남긴 것

- **커버리지** — 몇 %의 회사가 XBRL 인스턴스를 갖는가. 1차에서 "없음" 4건이
  나왔으나 **내가 쓴 corp_code가 틀려서**(`status=013`) 생긴 것이었고, 이름으로
  제대로 해석한 12개사는 **전부 XBRL이 있었다**. 그래도 전수는 안 쟀다.
- **「다름」의 상한** — 기간 축 필터가 무력이라 0.1%는 하한이다(§2-1 ⚠).

## 6. 1판에서 틀렸던 것 (기록)

지우지 않고 남긴다 — **어떻게 틀렸는지가 다음 사람에게 쓸모 있다.**

| 1판의 주장 | 왜 틀렸나 |
|---|---|
| *"XBRL이 원문 이름을 갖고 있다"* (CSA 사례) | 같은 금액을 가진 fact가 넷인데 **축을 안 보고** 그중 하나만 집었다. 포괄손익계산서 맥락의 fact는 API와 **같은** 이름이었다 |
| *"못찾음 43.1% → 0%"* | 사과와 오렌지였다. 감사보고서는 **다른 문서**이고 XBRL은 API와 **같은 원천**이라, 되짚기 100%는 당연하고 **새 정보가 없다는 뜻**이다 |
| *"SCE 28.4% → 41.6%"* | 그 41.6%도 라벨 합집합 매칭이라 부풀려진 값이고, 애초에 `account_detail`이 같은 정보를 **이미 주고 있었다** |
| *"권고: 계정명 대조 소스를 XBRL로"* | 위 셋이 무너지면 남는 이유가 없다 |

**공통 원인 하나** — 금액으로 되짚을 때 **맥락(축·기간)을 안 좁히면 합집합이 정답을
삼킨다**. 1판은 그 위험을 ⚠로 적어 두고도(*"다름 0.0%를 그대로 인용하면 안 된다"*)
권고는 그대로 냈다. **경고를 적는 것과 그 경고대로 판단을 미루는 것은 다르다.**
