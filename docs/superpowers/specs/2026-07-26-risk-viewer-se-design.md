# 리스크 뷰어 스페셜 에디션(SE) 설계

작성일: 2026-07-26
상태: 초안 — 사용자 리뷰 대기

---

## 1. 목적

기존 [리스크 뷰어](../../../docs/tool/index.html)는 "설치 없이 맛보기"용 공개 도구로, DART 엔드포인트 5개와 **공시 제목 키워드 매칭**만으로 동작한다. SE는 같은 회사를 훨씬 깊게 보는 **인가제 웹 서비스**로, 기존 뷰어와 사용자층이 분리된다.

SE가 기존 뷰어 대비 추가로 닿는 것:

| 층 | 내용 | 기존 뷰어 | SE |
|---|---|---|---|
| 1. 구조화 API | 재무·채무잔액·자금사용·내부자 지분·타법인출자·감사의견·배당 (엔드포인트 40여) | 5개 | 전부 |
| 2. 공시 원문(ZIP) | **CB/BW 인수자 실명**, 자금 사용 목적, 주석 카테고리, 계약 상대방 | ✗ | ✓ |
| 3. 행위자 대조 | 레지스트리 실명, sightings, 임원 겸직 | ✗ | ✓ **SE 독점** |

**화면의 척추는 돈(자금 흐름), 그 위에 사람(행위자)을 얹는다.** 시간축은 보조 레인으로 병행한다.

돈을 척추로 삼은 이유: 자금 흐름은 끊긴 지점이 스스로 드러나므로, 판정 문장 없이 사실 나열만으로 완결된다. 무점수 원칙(§9)과 충돌하지 않으면서 가장 강하게 말하는 구조다. 사람을 척추로 세우면 "이 사람이 문제다"에 가까워져 그 선을 계속 시험받는다.

## 2. 비범위

[CLAUDE.md](../../../CLAUDE.md)의 v1.0 GA 비범위를 SE도 그대로 승계한다. 특히:

- **점수·등급 부여 금지** (v0.8.5 원칙) — SE는 실명을 다루므로 오히려 더 엄격히 적용한다

## 3. 아키텍처

**호스팅: Vercel** (단일 호스트). Vercel Functions의 두 제약이 설계를 규정한다 — §3.3.

```
[브라우저]                  [Vercel Functions (Python)]         [외부]
  DART 키 보관                se_server/ (신규 패키지)
  (localStorage)                ├ 인증 가드          ──────────▶ Supabase Auth (REST)
  요청마다 동봉  ─────────▶     ├ 청크 오케스트레이터 ─────────▶ Supabase Postgres (작업 상태)
                                ├ 캐시 계층          ──────────▶ Supabase Storage (원문 ZIP)
  진행 폴링 ◀──────────────     └ dart_risk_mcp.core ──────────▶ DART API (사용자 키)
  섹션별 렌더                        (import만, 수정 없음)  ────▶ Notion 레지스트리 (제작자 키)
```

### 3.1 패키지 경계 — 가장 중요한 제약

`dart_risk_mcp/` core는 **절대 오염시키지 않는다.** CLAUDE.md의 "외부 라이브러리 추가 금지"(`requests`+`mcp`만)는 MCP 서버가 가볍게 설치되게 하는 원칙이다.

- SE 서버는 `se_server/` **별도 최상위 패키지**로 둔다
- 의존 방향은 `se_server` → `core` **단방향**이다. core는 `se_server`를 참조하지 않는다
- core의 런타임 의존성은 `mcp`+`requests`로 유지한다. SE 의존성(Supabase 등)은 core에 들어가지 않는다
- 결과: `pip install`로 MCP를 쓰는 사용자는 SE 의존성을 설치하지 않으며, SE의 존재를 알 필요도 없다

core에 변경이 필요하다고 판단되면, 그 변경이 **MCP 도구에도 독립적으로 유용한지**를 먼저 확인한다. 아니라면 SE 쪽에 둔다.

**승인된 core 변경 1건 — HTTP 캐시 시임.**

`_retry()`는 DART의 모든 트래픽(구조화 JSON·원문 ZIP)이 지나는 단일 진입점이다. 반면 원문을 소비하는 공개 함수들(`fetch_disclosure_full`·`list_document_sections`·`scan_note_titles`·`fetch_document_content`)은 전부 `(rcept_no, api_key)`만 받고 내부에서 `_fetch_document_zip`을 호출하므로, **밖에서 캐시된 ZIP을 주입할 구멍이 없다.**

따라서 `_retry`에 선택적 캐시 훅 `set_http_cache(cache)`를 추가한다. 기본값 `None`이며 이 경우 동작은 현행과 완전히 동일하다 — MCP 서버는 이를 설정하지 않는다. 이 변경은 위 예외 조건을 통과한다: MCP 서버 역시 같은 ZIP을 반복 내려받고 있어 동일한 훅으로 이득을 볼 수 있다.

대안이었던 private 함수(`_fetch_document_zip`) 몽키패치는 core 리팩터링 시 조용히 깨지므로 채택하지 않는다.

**이 1건 외에 core 수정은 없다.** 캐시 키 계산·정책 분기·저장소 접근은 전부 `se_server` 쪽에 둔다.

### 3.2 기술 스택 (제안 — 확정 필요)

| 층 | 선택 | 이유 |
|---|---|---|
| 호스팅 | **Vercel** (Python Functions) | 단일 호스트 유지. 제약은 §3.3 |
| 인증 | **Supabase Auth를 REST로 호출** | `supabase-py`는 `gotrue`/`postgrest`/`storage3`/`realtime`을 끌고 온다. 우리가 쓰는 건 `/auth/v1/token`·`/auth/v1/user` 정도라 SDK 값어치가 없다. `requests`로 충분 |
| 작업 상태 | Supabase Postgres | 청크 실행의 진행 상태 (§7.3) |
| 캐시 | Supabase Storage + Postgres 메타 | §6.2 |
| 프론트 | vanilla JS 단일 HTML | 기존 뷰어(77KB 단일 파일)와 같은 패턴. 빌드 도구 없음 |

### 3.3 Vercel 제약이 설계에 미치는 영향

Vercel Functions의 두 성질이 설계를 규정한다. 둘 다 우회 불가이며, 설계가 여기에 맞춰야 한다.

| 제약 | 근거 | 설계 귀결 |
|---|---|---|
| **파일시스템 비영속** | 실행 간 샌드박스가 초기화된다. `/tmp`는 인스턴스 수명만큼만 유지 | 디스크 영구 캐시 불가 → **Supabase Storage**로 이전 (§6.2) |
| **함수 실행 시간 상한** | `maxDuration` 상한이 분 단위. 콜드 실행 8–15분을 단일 요청이 버티지 못한다 | 단일 SSE 스트림 불가 → **청크 실행 + 폴링** (§7.3) |

두 번째 제약의 부수 효과: 향후 확장으로 미뤄뒀던 **작업 상태 관리가 1차 구현에 필요해진다.** 다만 워커·메시지 브로커가 아니라 **진행 상태 테이블 + 재개 가능한 청크 함수** 수준이다.

대안으로 분석 워커만 별도 호스트(Fly·Railway 등)에 두면 SSE 설계를 그대로 유지할 수 있으나, 호스트가 둘로 늘고 운영 표면이 커진다. **Vercel 단일 유지를 우선한다.**

## 4. 인증·계정

- **규모 전제:** 수십 명, 증가 예정. 가입은 제작자 인가를 거친다
- **Supabase 담당 범위:** 로그인·세션·계정 관리 **만**
- **DART 키:** 브라우저 `localStorage`에만 보관하고 요청마다 동봉한다. **서버에 저장하지 않는다**
  - 서버가 뚫려도 사용자 키는 유출되지 않는다
  - 비용: 기기를 바꾸면 키를 다시 입력해야 한다 (기존 뷰어와 동일한 UX라 학습 비용 없음)
  - **불가피한 사실:** 원문 독해를 서버가 수행하므로 키는 반드시 서버를 **통과**한다. "서버가 키를 볼 일이 없다"는 상태는 만들 수 없다. 저장하지 않는다는 약속만 지킬 수 있으며, 이를 UI와 문서에 명시한다

## 6. 3단 로딩 + 캐시

### 6.1 로딩 단계

| 단 | 대상 | 산출 | 시간 (콜드) |
|---|---|---|---|
| **1단 — 항상** | 구조화 API 40여 개 (원문 0건) | 재무이상·채무·자금사용·내부자·출자·감사의견·배당 | ~40초 |
| **2단 — 항상** | **신호 매칭 공시 원문 전부** (8개 카테고리) + 최근 사업보고서 3건 | 인수자 실명, 자금 용도, 주석 카테고리, R&D 비중, XBRL 감가상각비 | 8–15분 |
| **3단 — 클릭 시** | 나머지 공시 | 우측 패널에서 요청 시 로드 | 건당 1–3초 |

콜드 실행 총 **~250콜 / 8–15분**. DART 일 한도 20,000건 기준 사용자당 하루 약 80개 회사.

### 6.2 캐시 — 처음부터 구현한다

**핵심 사실: `rcept_no`는 불변 식별자이고, 원문 ZIP도 불변이다.** 정정공시는 기존 문서를 수정하지 않고 **새 `rcept_no`를 발급받는다.** 따라서 원문 캐시에는 stale 문제가 없다.

| 캐시 | 저장처 | 키 | TTL | 근거 |
|---|---|---|---|---|
| 공시 원문 ZIP | **Supabase Storage** | `rcept_no` | **영구** | 불변. 정정은 새 번호 |
| 구조화 API 응답 | Supabase Postgres | `(endpoint, corp_code, bsns_year, reprt_code)` | 7일 | 확정 연도는 불변이나 최근 연도는 정정 가능 |
| corp_codes | Postgres | — | 24시간 | 기존 core 동작 유지 |
| 레지스트리(Notion) | Postgres | — | 24시간 | 기존 core 동작 유지 |

Vercel 파일시스템이 비영속이므로(§3.3) 캐시는 **외부 저장소**여야 한다. 이미 인증에 Supabase를 쓰므로 Storage/Postgres를 그대로 활용한다 — 신규 벤더가 늘지 않는다.

- 원문은 **공개 데이터**이므로 사용자 간 캐시 공유가 가능하다. A가 받아둔 사업보고서를 B가 재사용해도 무방하며, 어느 사용자 키로 받았는지는 무관하다. 외부 저장소로 옮기면 이 공유 이점이 오히려 강해진다 (인스턴스 경계가 사라짐)
- 기대 효과: 같은 회사 2회차부터 **8–15분 → 30초~1분**
- 현 core의 `_zip_cache`(메모리 5건·10분 TTL)는 서버용으로 너무 작다. SE는 **캐시 계층을 별도로** 두고 core 함수를 감싼다 (core 수정 없이 — §3.1)
- **주의:** 원문 ZIP은 사용자 DART 키로 받지만 캐시는 전 사용자가 공유한다. 캐시 키에 사용자 식별자를 **넣지 않는다** — 넣으면 공유 이점이 사라진다

캐시를 나중에 붙이면 캐시 키 설계 때문에 오케스트레이터를 다시 뜯게 되므로 **1차 구현에 포함한다.**

## 7. 화면 설계

**골격: 롱스크롤 본문 + 우측 슬라이드 패널.**

본문은 위에서 아래로 한 줄기로 흐르고, 본문 안의 **사람 이름·공시 제목을 클릭하면 우측에서 패널이 밀려나온다.** 본문 스크롤 위치를 잃지 않는다.

이 골격을 고른 이유: SE의 유일한 독점 자산은 행위자 실명인데, 별도 섹션에 격리하면 자금 체인을 읽다 인물을 만나도 "나중에 보자"가 되고 대부분 보지 않는다. 슬라이드 패널은 **돈을 읽는 그 자리에서 사람이 열린다** — 돈을 척추로, 사람을 그 위에 얹기로 한 결정과 구조가 일치하는 유일한 안이다.

### 7.1 본문 섹션 순서

| # | 섹션 | 내용 | 로딩 단 |
|---|---|---|---|
| 0 | 헤더 | 회사명·종목코드·업종·대표자·조회 시점·조회 범위 | 1 |
| ① | **계획 vs 실제 요약** | 공시된 자금 용도 ↔ 실제 집행을 좌우 대조. 어긋난 지점만 부각 | 1+2 |
| ② | **자금 체인** | 조달건별 수직 흐름도. 폭이 금액에 비례. 조달 → 계획 → 집행 → 도착지 손익 | 2 |
| ③ | **자금 시계열 레인** | 시간축 위 유입(위)/유출(아래). 조달·유출의 박자 | 1+2 |
| ④ | 재무 이상 | `scan_financial_anomaly` 8플래그 + Beneish 개별 변수 + 지표 7종 YoY | 1 |
| ⑤ | 지배구조 | 최대주주 변동·5% 대량보유·내부자 시계열·임원 | 1 |
| ⑥ | 감사·부실 | 감사의견 이력·연속적자·채무 만기·부실 이벤트 | 1 |
| ⑦ | 공시 원문 열람 | 섹션 드릴다운 진입점 | 3 |
| ⑧ | 출처·면책 | 데이터 출처, 동명이인 경고, 무판정 고지 | — |

①이 3초 요약이고 ②가 본문이다. ①만으로는 얕고 ②만으로는 스크롤을 요구하므로 둘 다 둔다.

### 7.2 우측 슬라이드 패널

| 트리거 | 패널 내용 |
|---|---|
| 인물 이름 클릭 | 레지스트리 status, 등장 회사 목록, 근거 공시 링크, **동명이인 경고**, sightings 요약 |
| 공시 제목 클릭 | 원문 섹션 목록 → 본문 페이지네이션 (3단 로딩) |
| 피출자 법인 클릭 | 타법인 출자현황 상세, 해당 법인 손익 |

### 7.3 점진 렌더 (청크 실행 + 폴링)

콜드 실행이 8–15분이라 일괄 렌더는 성립하지 않고, Vercel 함수 시간 상한(§3.3) 때문에 단일 SSE 스트림도 성립하지 않는다. 대신 **작업을 청크로 쪼개 여러 함수 호출에 나눠 싣는다.**

| 요소 | 동작 |
|---|---|
| `POST /analyze` | 작업 레코드 생성(회사·범위·단계별 할 일 목록) → `job_id` 반환 |
| `POST /analyze/{job_id}/step` | **60초 내에 처리 가능한 만큼만** 진행하고 상태를 Postgres에 적재 후 반환. 남은 일이 있으면 `done: false` |
| `GET /analyze/{job_id}` | 현재까지 완성된 섹션 데이터 + 진행률 반환 |
| 브라우저 | `step`을 `done`이 될 때까지 반복 호출하며, 매 응답의 완성 섹션을 **위에서부터 채워 내려간다** |

```
t=0     헤더 렌더 + "① 요약 계산 중…"
t≈40s   ①④⑤⑥ 렌더 (1단 완료)
t≈2m    ② 자금 체인 부분 렌더 (원문 도착 순)
t≈15m   전체 완료
```

사용자가 보는 화면 거동은 SSE 안과 동일하다. 로딩 순서(1단→2단→3단)와 섹션 순서가 같은 방향이므로 청크 경계를 단계 경계에 맞추면 된다.

**설계상 이점:** 작업 상태가 Postgres에 남으므로 **중단·재개가 공짜로 따라온다.** 브라우저를 닫았다 다시 열어도 진행 중인 작업을 이어받는다. 이는 다음 항목으로 자연히 확장된다 — 여러 회사를 걸어두고 나중에 확인하는 **작업 목록**은 이제 별도 인프라 없이 상태 테이블 조회만으로 구현된다.

**주의:** 브라우저가 `step`을 구동하므로, 탭이 닫히면 진행이 멈춘다(상태는 보존되나 자동 재개는 없다). 서버 주도 자동 완주가 필요해지면 별도 워커 호스트가 필요하며, 이는 1차 범위 밖이다.

## 8. 오류 처리

- **섹션 단위 격리:** 한 섹션의 API가 실패해도 나머지는 렌더한다. 실패 섹션은 사유를 표시한다. SSE 구조상 자연스럽게 성립한다
- **DART 오류 코드:** 기존 뷰어의 `DART_ERR` 매핑(010 미등록 키 / 011 미활성 / 020 한도 초과 / 800 점검)을 재사용한다
- **원문 파싱 실패:** 해당 공시만 건너뛰고 목록에 "원문 읽기 실패"로 남긴다. 조용히 누락시키지 않는다
- **레지스트리 미설정:** Notion 자격증명이 없으면 행위자 층 전체를 비활성화하고 그 사실을 표시한다 (core의 graceful 비활성화 동작 계승)
- **부분 실패 고지:** 완료 시 "N개 섹션 중 M개 실패"를 헤더에 표기한다. 결측을 성공처럼 보이게 하지 않는다

---

## 9. 무점수 원칙 준수

SE는 심층·실명을 다루므로 "그래서 위험한가?"라는 압력이 기존 도구보다 강하다. 다음을 강제한다:

- 위험 등급·종합 점수·이모지 신호등을 **어떤 형태로도** 렌더하지 않는다
- 내부 정렬용 `SIGNAL_TYPES[*].score`·`taxonomy.base_score`는 렌더 경로로 유출되지 않는다
- 플래그는 **사실 라벨**로만 표기한다 (`FUND_DIVERSION` = "계획 용도와 집행 불일치")
- 행위자 표기는 status와 동명이인 경고를 항상 동반한다

기계적 검증: [tests/test_golden_output_hygiene.py](../../../tests/test_golden_output_hygiene.py)의 점수/등급/이모지 회귀 검사를 **SE 렌더 출력에도 확장 적용**한다.

## 11. 미결정 사항

1. **개인정보 처리방침** — 이메일 수집 + 실명 데이터 취급이므로 법적으로 필요하다. 코드가 아닌 문서 작업이며 착수 전 일정에 반영해야 한다
2. **Vercel 요금제** — `maxDuration` 상한이 플랜에 따라 다르므로 청크 크기를 실측해 정해야 한다. 배포 후 1회 실측 필요
3. **레지스트리 정정 반영 경로** — Notion에서 인물을 삭제·정정했을 때 캐시된 SE 화면에 어떻게 반영할지 (24시간 캐시 TTL로 충분한지)
4. **초기 인가 절차** — 가입 신청 → 제작자 승인의 구체적 흐름
5. **Notion 토큰 보관** — Vercel 환경변수에 상주한다. 회전 주기·접근 통제 방침 필요

## 12. 결정 이력

| 결정 | 선택 | 대안을 버린 이유 |
|---|---|---|
| 심화 방향 | 넓게(A) + 깊게(B) 동등, 서사(C) 후순위 | — |
| 배포 형태 | 인터넷 호스팅 서비스 | 파일 배포형은 회수 불가·로그 0·**정정 경로 부재**. 실명을 다루는 이상 성립하지 않음 |
| 행위자 실명 | 포함 | SE의 유일한 독점 자산 |
| 인증 | Supabase (REST, 좁게) | 자체 구현은 비밀번호 재설정·메일 서버까지 끌고 옴 |
| DART 키 | 브라우저 보관 | 서버 저장은 유출 표면 확대 |
| 화면 골격 | 롱스크롤 + 우측 슬라이드 패널 | 탭·별도 섹션은 행위자를 격리시킴 |
| 원문 범위 | 신호 매칭 공시 전부 | 좁히면 SE의 "특별함"이 사라짐. 시간은 캐시로 회수 |
| 대기 UX | 청크 실행 + 폴링 점진 렌더 | 일괄 렌더는 15분 빈 화면. SSE 단일 스트림은 Vercel 시간 상한에 막힘 |
| 캐시 | 1차 구현에 포함, Supabase Storage | 나중에 붙이면 오케스트레이터 재작업. Vercel 파일시스템은 비영속 |
| 호스팅 | Vercel 단일 | 별도 워커 호스트는 운영 표면이 둘로 늘어남 |
| 유출 통제 | 구현 안 함 | 사용자 결정 |
